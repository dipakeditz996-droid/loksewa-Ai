# LoksewaAI — Own Payment OCR Verification + Automatic Validation + Admin Review System

We are continuing development of the existing LoksewaAI platform.

The current Student → Package Checkout → Payment Submission flow is failing with an HTTP 500 error when submitting payment details.

The goal of this task is to:

1. Fix the existing payment submission 500 error.
2. Build an internal payment screenshot OCR and verification system.
3. Do NOT depend on an external AI API for basic payment verification.
4. Extract payment information from uploaded screenshots using our own OCR pipeline.
5. Validate extracted information against the expected package/payment data.
6. Automatically classify payments as:

   * Automatically Verified / High Confidence
   * Needs Admin Review
   * Rejected
7. If OCR cannot confidently verify the payment, NEVER immediately cancel the payment.
8. Instead show:

   > "Payment could not be automatically verified. Your payment has been sent for Admin approval."
9. Allow Admin to manually verify the screenshot later.
10. Provide temporary/provisional access only according to the safe verification rules defined below.
11. Keep the existing Django → PostgreSQL/Supabase architecture.
12. Do NOT create a second payment/authentication architecture.


# 10. AMOUNT VALIDATION

```text
OCR Amount

Expected Payment Amount
```

```text

```

```text

```

If not:

```text

```

Do NOT automatically approve a payment merely because the amount matches.

Amount is only one verification signal.

# 16. SCREENSHOT TAMPERING / MANIPULATION HEURISTICS

Do NOT claim that the system can perfectly detect AI-generated or edited screenshots.

Instead implement a conservative:

```text
image_integrity_status
```

using available non-AI heuristics.

Possible checks:

* image metadata where available
* image dimensions
* suspicious re-encoding
* inconsistent text rendering where technically detectable
* OCR layout consistency
* unexpected duplicated regions
* suspicious visual artifacts
* impossible payment formatting
* mismatch between extracted fields
* duplicate image hash
* duplicate transaction ID

Calculate a:

```text
suspicion level
```

only if the implementation has real evidence.

Possible:

```text
NORMAL
SUSPICIOUS
UNKNOWN
```

Do NOT label an image:

> "AI Generated"

unless there is a genuinely validated detector.

Prefer wording:

> "Potentially suspicious receipt"

instead of claiming certainty.

# 20. AUTOMATIC VERIFICATION RULE

Only automatically verify when the payment satisfies a conservative set of real checks.

For example:

```text
Amount matches
AND
transaction ID exists
AND
transaction ID is not already used
AND
receiver matches where available
AND
no serious integrity/suspicion issue
AND
OCR extracted required information with sufficient confidence
```

Do not require every optional field if the receipt legitimately doesn't contain it.

Do not invent a numerical "92% genuine" score without a defensible model.

Prefer explicit rule results.

```text

```

Conceptually:

```text

Permanent      Revoke access
```

If the existing business requirement wants automatic approvals to remain final, do not invent unnecessary manual review. However, if provisional access is implemented, make it clearly revocable and auditable.

# 46. IMPORTANT — DO NOT CLAIM "100% FRAUD DETECTION"

This system is a:

> **Payment Receipt OCR + Rule-Based Verification System**

It is NOT a bank/payment gateway verification API.

A screenshot alone cannot cryptographically prove that money actually reached the account.

Therefore UI wording should be conservative:

Good:

> Automatically verified

> High-confidence receipt match

> Waiting for Admin approval

Bad:

> 100% genuine payment

> AI confirmed this payment is real

> Money definitely received

Unless the platform later integrates with an actual payment provider API/bank statement reconciliation system.
